# Vehicle Model Layered Architecture — Implementation Status

**Read this first if you're picking this work up in a new session.** It records what was done, why, what's left, and how to verify it.

## Audit follow-up (2026-11-04) — read this first

The audit in `docs/audit/` (v1, v2 reports) listed bugs B01–B30. This round fixed the remaining ones; the key changes for anyone resuming vehicle-model work:

- **`VehicleState::steering_angle`** now carries the wheel angle actually applied by the actuator; every vehicle model writes it and LQR/MPC/MPPI plan from it.
- **`ComposedVehicleModel`** integrates the **rear axle** (lateral velocity `vy − b·r`), sub-steps at ≤ 2 ms, runs the steering actuator before the low-speed fallback, projects the front tire force with the steering angle, and seeds its actuator from the incoming state (a rebuilt model keeps the wheel angle).
- **`vehicle::TireAngleLimits`** — `minimum_turning_radius` is authoritative (`|δ| ≤ atan(L/R)`), and left/right travel may differ. Bus 01 is limited to 43.3°, Car 01 to 26.1°.
- **Maps are in metres** for every vehicle (the old per-vehicle `vehicle_radius` scale is gone). map_01/map_03 paths were clothoid-smoothed with `tools/smooth_path.py`, map_02 regenerated by `tools/generate_map02_path.py`; both check bends and body clearance in metres.
- **Simulation loop** is fixed-step (1/60 s) with shared rules in `src/sim/sim_rules.cpp`: limited speed command (vehicle `max_acceleration` / `max_deceleration` / `max_jerk`), goal line, Failed on collision / off-map / timeout.
- Tests live in `tests/` (`ctest`), CI in `.github/workflows/ci.yml`.

(The "12 m fillet" mentioned below was 12 *map units*, i.e. 8.75 m for Car 01 at the time; with maps now in metres the fillets are ~12 m for both vehicles.)

## Follow-up: map path realism + initial-heading fix (this session)

The user reported that MPC + Car 01 + "Dynamic (Linear Tire)" couldn't complete the first turn on `map_03` ("Trapezoidal Course"), and separately that **no** algorithm could stay on the road on `map_01`/`map_02` under Dynamic fidelity ("vehicle not starting parallel to the road... kinematic model easily handles them why would it be?"). Root cause was the same underlying mechanism in both cases, just triggered two different ways:

- `ModelFidelity::Kinematic` (`KinematicBicycleModel`) never reads `VehicleData::steering` at all, so it can snap its heading/steering to whatever's needed almost instantly — it's immune to unrealistic path geometry or a bad initial heading.
- `ModelFidelity::DynamicLinearTire` uses `RateLimitedSteeringModel` (real `max_steering_wheel_rate`, ~12.9°/s for Car 01) plus `LinearTireModel`'s friction-circle slip-angle saturation. A real plant with those limits **cannot** execute an instantaneous heading change.

Two independent bugs fed that mismatch:
1. **`map_03/path.json`** had a ~104° heading discontinuity at a single waypoint (110, 20) — verified by exact collinearity check, it was two straight lines meeting at a point, not a curve at all — plus a second ~76° kink at (90, 100). `map_01/path.json` had three kinks (14°/47°/12°) at its slalom gaps. Both are geometrically impossible for any rate-limited steering system to track, regardless of vehicle model.
2. **`src/vehicle_control_ui.cpp`**, `InitSimulation()` hardcoded `simVehicleState_.heading = 0.0f` (due east) regardless of the loaded path's actual starting direction. `map_02`'s path starts at heading ≈70°, `map_01`'s at ≈−9°, `map_03`'s at 0° (coincidentally matching). Under Kinematic fidelity this initial mismatch is corrected almost instantly; under Dynamic fidelity, the rate-limited steering takes ~1+ second to correct a 70° error, during which the speed controller keeps accelerating while still misaligned, producing a large lateral excursion off the road.

Fixes:
- `src/vehicle_control_ui.cpp:378` — `simVehicleState_.heading` is now computed as `atan2(path.waypoints[1].y - path.waypoints[0].y, path.waypoints[1].x - path.waypoints[0].x)` instead of a hardcoded `0.0f`. Generic fix, applies to all current and future maps.
- `data/maps/map_01/path.json` and `data/maps/map_03/path.json` regenerated: the same corner waypoints (same overall route, same obstacle-avoidance intent) but with each sharp corner replaced by a tangent-arc fillet of radius 12 m (~2.3× Car 01's `minimum_turning_radius` of 5.3 m, ~2.6× Bus 01's 4.6 m) instead of an instantaneous kink. Max heading change between consecutive waypoints dropped from 47–104° to ≤6°. Regenerated via a one-off Python script (not checked into the repo); obstacle clearance re-verified computationally (min clearance ≥2.4 m beyond `vehicle_radius` on both maps). `map_02/path.json` was left unchanged — its curve was already smooth throughout; only the start-heading mismatch needed fixing, which the code fix above handles.

`vehicle_model_tests` still passes 14/14 (unaffected — synthetic in-code data, no map/path dependency). **Not yet manually verified in the running GUI** — next session (or the user) should re-run MPC/Car 01/Dynamic on map_03's first turn and any algorithm on map_01/map_02 under Dynamic fidelity to confirm the swerve-off-road behavior is gone.

## Follow-up: dead-code cleanup pass (this session)

- **`DrivetrainParams`/`AeroParams`** — removed from `vehicle_data.hpp` (structs), `VehicleData` (the `drivetrain`/`aero` members), and `vehicle_loader.cpp` (their guarded JSON parse blocks). Their `enabled` flags were written by the loader but never read by any consuming code.
- **`VehicleDebugInfo`, `DebugInfo()`, `MaxStableDt()`, `Name()`** — removed from `IVehicleModel` and both implementations (`KinematicBicycleModel`, `ComposedVehicleModel`). All four had declarations/overrides but zero callers anywhere. `IVehicleModel` is now just `Step()` + a virtual destructor.
- **`WheelState`, `VehicleState::wheels`** — removed from `vehicle_state.hpp`. Declared, never read or written anywhere.

All builds clean, and `vehicle_model_tests` still passes 14/14 (the removed code had no test coverage depending on it, since nothing used it). Both `vehicle_dynamics_architecture.drawio` (all 5 pages) and `vehicle_dynamics_guideline.html` were updated to match — the dead-code box-cards/diagram cells are gone, not just re-labeled.

**Not re-verified in the running GUI** after this pass — next session should do a basic sanity run (any vehicle, either fidelity) to confirm nothing regressed, though the successful build + full test pass make a runtime break unlikely.

## Purpose

The user reviewed `vehicle_dynamics_guideline.html` + `vehicle_dynamics_architecture.drawio` (same folder) — a planning doc proposing a layered vehicle model architecture (`IVehicleModel` + swappable tire/suspension/drivetrain/aero/steering subsystems, composed by `ComposedVehicleModel`) to replace the current kinematic-only plant. They specifically liked the "Proposed Layered Architecture" diagram and asked to **implement it in real C++**, following **SOLID, OOP, and Clean Code** — matching this codebase's existing conventions rather than generic boilerplate.

Scope chosen by the user: **Level 1 + 2** of the guideline's staged roadmap (the full layered architecture, using only parameters already available — no OEM-only data like Pacejka coefficients or measured suspension spring rates), **with live UI wiring**, **plus a small dependency-free smoke-test suite**. Level 3 (quarter-car suspension, torque drivetrain, 4-wheel state, fixed-timestep integration fix) and Level 4 (ABS/ESP) were explicitly deferred — see "What's NOT done" below.

## What was implemented

### New library code (`include/vehicle/`, `src/vehicle/`)

- **`i_vehicle_model.hpp`** — `IVehicleModel` interface (mirrors `path_tracking::IPathTrackingAlgorithm`) + `VehicleDebugInfo`.
- **`vehicle_model_factory.{hpp,cpp}`** — `enum class ModelFidelity { Kinematic, DynamicLinearTire }` + `MakeVehicleModel(fidelity, data)`. The **only** place a concrete subsystem class is named (Dependency Inversion anchor).
- **`composed_vehicle_model.{hpp,cpp}`** — `ComposedVehicleModel : public IVehicleModel`, the composition root. Holds a `Subsystems` struct of `unique_ptr<Ixxx>` abstractions; `Step()` delegates to small private helpers (`UpdateSteering`, `UpdateAxleLoads`, `ComputeTireForces`, `ComputeDrivetrainForce`, `ComputeAeroForce`, `IntegrateDynamics`, `KinematicFallback`).
- **`math_utils.hpp`** — shared `Clamp<T>`/`Lerp<T>`, extracted because the clamp idiom was about to be duplicated a 7th time (it already existed 4x in `stanley.cpp`/`mpc.cpp`/`mppi.cpp`/`vehicle_bicycle_model.cpp`).
- **`tire/`** — `ITireModel` + `LinearTireModel` (extracts `DynamicBicycleModel`'s dead `Fy=C·α` math, adds a friction-circle clamp).
- **`suspension/`** — `ISuspensionModel` + `RigidSuspensionModel` (Gillespie/Wong algebraic load transfer; reduces to today's static split when `cog_height==0`).
- **`drivetrain/`** — `IDrivetrainModel` + `DirectAccelDrivetrainModel` (`Fx = mass·u_a`, bit-for-bit regression anchor).
- **`aero/`** — `IAeroModel` + `SimpleAeroModel` (`Fx = -mass·CA·vx·|vx|`, bit-for-bit regression anchor).
- **`steering/`** — `ISteeringModel` + `InstantaneousSteeringModel` (today's clamp-only behavior) + `RateLimitedSteeringModel` (**activates `VehicleData::max_steering_wheel_rate`**, parsed since day one but never read by any model until now).
- **`overlay/i_control_overlay.hpp`** — `IControlOverlay` interface only, **no implementation**. Deliberate Level-4 stub (ABS/ESP) — documented as intentionally undone, not wired into `ComposedVehicleModel::Subsystems` yet (avoids speculative complexity).

### Modified existing files

- **`vehicle_bicycle_model.{hpp,cpp}`** — both `KinematicBicycleModel` and `DynamicBicycleModel` now implement `IVehicleModel` (`Step()` lost `const`, gained `override`; added `MaxStableDt()`/`DebugInfo()`/`Name()`). **Zero equation changes** — verified by direct diff before/after. `DynamicBicycleModel` itself is still never instantiated by the factory (its math lives on inside `ComposedVehicleModel` + `LinearTireModel` + `RigidSuspensionModel` now) — it remains dead code, just interface-compliant.
- **`vehicle_data.hpp`** — added `cog_height` (flat, guarded parse) + 5 nested param structs in `namespace vehicle` (`TireParams`, `SuspensionParams`, `DrivetrainParams`, `AeroParams`, `SteeringParams`), each with an `enabled` flag defaulting to reproduce today's exact behavior. `VehicleData` itself stays global-scope (pre-existing inconsistency, deliberately not touched).
- **`vehicle_state.hpp`** — appended `WheelState` struct + `std::array<WheelState,4> wheels` (unused scaffolding for a future 4-corner model; append-only, confirmed safe — no positional construction of `VehicleState` anywhere in the codebase).
- **`vehicle_loader.cpp`** — guarded (`has()`-checked) parsing for the 5 new nested JSON blocks + `cog_height`. Old `vehicle01.json`/`vehicle02.json` parse identically (no changes needed to those files). Noted but **deliberately did not fix** the pre-existing unconditional-overwrite bug in the original 20-field parse block (out of scope, harmless today, flagged as a follow-up).
- **`CMakeLists.txt`** — added the 8 new `.cpp` files to the main target, plus a new **`vehicle_model_tests`** executable target (no ImGui/GLFW/OpenGL dependency) + `enable_testing()`/`add_test()`.
- **`vehicle_control_ui.{hpp,cpp}`** — see UI wiring below.

### UI wiring

- New **"Vehicle Model"** picker on the **simulation screen** (not the main screen — deliberate: main-screen selections are hard prerequisites that reset the whole scenario; model fidelity has a safe default and the actual use case is comparing fidelity **mid-run**, which requires *not* resetting).
- `selectedVehicleModelKind_` / `kAvailableVehicleModels` (`"Kinematic"`, `"Dynamic (Linear Tire)"`), `modelDirty_` flag, `RebuildVehicleModel()` — mirrors the existing `selectedAlgorithm_`/`paramsDirty_`/`RebuildAlgorithm()` pattern exactly.
- `simModel_` is now `unique_ptr<vehicle::IVehicleModel>` (was `unique_ptr<KinematicBicycleModel>`). Of the 6 original call sites, 4 needed zero textual change (ctor init, `.reset()`, null-check, `Step()` call) — only the header type and `InitSimulation()`'s construction line changed.
- Fidelity swap **never resets `simVehicleState_`** — safe in both directions by construction (see code comments in `RebuildVehicleModel()` for the reasoning).
- New `TuneTire`/`TuneSuspension`/`TuneSteering` structs + sliders (Cornering Stiffness, CoG Height, Rate-Limited Steering toggle + Max Steering Rate), following the exact `sliderF`/checkbox/tooltip pattern already used for algorithm tuning.
- Added a "Model" row to the Simulation Info panel.

### Tests

- **`tests/vehicle_model_tests.cpp`** — plain `int main()`, no framework (matches the project's zero-dependency style). 12 checks: Kinematic regression (straight-line/heading/x/speed sanity), factory-vs-direct equivalence over 50 steps, `LinearTireModel` (unsaturated + friction-clamped), `SimpleAeroModel` (forward + reverse drag), `DirectAccelDrivetrainModel` (Bus 01/Car 01 mass cases), `RateLimitedSteeringModel` (ramp-up/settle/reversal).
- **All 12 pass.** Run via `./vehicle_model_tests` (exit 0/1) from the build dir, or `ctest -R vehicle_model_tests --output-on-failure`.

## Bugs found during manual testing (both fixed)

1. **Panel collision**: the Vehicle Model tuning panel's height budget was smaller than its actual content, so it visually overlapped the algorithm-tuning panel below it. **Fix**: both `RenderVehicleModelTuning`'s subsystem sliders and `RenderParamTuning`'s slider list are now each wrapped in their own bounded/scrollable `ImGui::BeginChild` region — content scrolls instead of bleeding into the sibling panel, regardless of algorithm/subsystem count.
2. **Popup off-screen**: the "Select Vehicle Model" popup opened anchored near its button (bottom-right of the panel) with no explicit position, clipping off the window edge. **Fix**: explicitly centered via `ImGui::SetNextWindowPos(GetMainViewport()->GetCenter(), ImGuiCond_Appearing, ImVec2(0.5f,0.5f))`, same pattern Dear ImGui's own demo uses for modals.

Both fixes are in and the GUI target rebuilds clean. **These specific fixes have not yet been re-confirmed visually by a human** — the user asked to take over manual testing themselves rather than have the agent keep driving the UI via `xdotool`. Next session should ask whether that testing happened and what (if anything) still looks wrong.

## What's NOT done (deferred, per user's chosen scope)

- **Level 3**: quarter-car suspension (spring/damper states), torque-based drivetrain, 4-wheel (`WheelState`) population, and the fixed-timestep-accumulator integration fix flagged in the guideline (explicit Euler becomes unconditionally unstable once a real suspension is added — not an issue yet since `RigidSuspensionModel` has no spring/damper states).
- **Level 4**: `IControlOverlay` has no concrete ABS/ESP implementation.
- **Pacejka/nonlinear tire model**: only `LinearTireModel` exists; `ModelFidelity::DynamicPacejkaTire` was deliberately not added as an enum value (no case = no dead value).
- **Existing-code cleanup flagged but not done**: the unconditional-overwrite bug in `vehicle_loader.cpp`'s original 20-field parse block; retrofitting `vehicle::Clamp()` into `stanley.cpp`/`mpc.cpp`/`mppi.cpp`'s existing duplicated clamp idiom.

## How to build & verify

```bash
cd build
cmake .. && make -j$(nproc)              # builds vehicle_control_algorithms + vehicle_model_tests
./vehicle_model_tests                     # expect: 12x "[ OK ]", "0 failure(s)", exit 0
./vehicle_control_algorithms               # launch the GUI
```

Manual test checklist (simulation screen, right panel):
1. Default fidelity is "Kinematic" — behavior should be unchanged from before this work.
2. Vehicle Model → "Model: Kinematic" button → popup should open **centered on screen**, fully visible → select "Dynamic (Linear Tire)" → applies live, sim does **not** reset.
3. Tire/Suspension/Steering sections should scroll internally if content doesn't fit, and must **not** visually overlap the "Parameter Tuning" (algorithm) panel below — check especially with LQR selected (13 sliders, the tightest case).
4. Sliders (Cornering Stiffness, CoG Height, Rate-Limited Steering + Max Rate) should be tunable and visibly affect vehicle behavior once their "Override ... Defaults" checkbox is on.
