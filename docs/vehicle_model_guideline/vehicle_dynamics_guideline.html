Vehicle Dynamics Model — Current Architecture

VehicleControlAlgorithms · what's actually built and running today: IVehicleModel, ComposedVehicleModel, five swappable subsystems, live UI wiring, and a test suite (14 vehicle unit checks plus edge-case and closed-loop scenario tests, see tests/).

Purpose & How to Read This

This document was originally a proposal for a layered vehicle model architecture. That proposal has since been implemented — this revision describes the system as it exists in the codebase right now, with detailed box diagrams of the actual classes, data flow, and files. It is no longer a "before/after" comparison; the layered architecture is the current architecture.

Companion diagram Open vehicle_dynamics_architecture.drawio (same folder) alongside this document — 5 pages, each referenced from the matching section below: System Overview, IVehicleModel Hierarchy, ComposedVehicleModel Composition, Data Model, and UI/Tests.

Badges used throughout: active code that runs today, data configuration/JSON.

Code cleanup A subsequent pass removed every piece of code confirmed to have zero callers anywhere in the codebase — DynamicBicycleModel, IControlOverlay, VehicleDebugInfo/DebugInfo()/MaxStableDt()/Name(), DrivetrainParams/AeroParams, WheelState, and an unused Lerp() helper. This document describes what's left: the actual, exercised architecture, with no unused scaffolding. See IMPLEMENTATION_STATUS.md for the full history.

    ▼
VehicleModelFactory::MakeVehicleModel(ModelFidelity fidelity, const VehicleData&)
    │
    ├─▶ ModelFidelity::Kinematic          → KinematicBicycleModel
    └─▶ ModelFidelity::DynamicLinearTire  → ComposedVehicleModel (5 subsystems)
    │
    ▼
simModel_ : unique_ptr<IVehicleModel>
    │  TickSimulation(dt): simModel_->Step(simVehicleState_, ctrl, dt)
    ▼
VehicleState  →  consumed identically by all 6 path-tracking algorithms

The key property this achieves: every path-tracking algorithm (Pure Pursuit, Adaptive Pure Pursuit, LQR, Stanley, MPC, MPPI) works unmodified against either model fidelity — none of them were touched to add the new fidelity, because they all depend only on the shared VehicleState/VehicleControls types, never on a concrete model class.

IVehicleModel & the Two Active Models

→ See diagram page 2 — "IVehicleModel Hierarchy and Factory" 
class IVehicleModel {
public:
    virtual ~IVehicleModel() = default;
    virtual VehicleState Step(const VehicleState& state,
                              const VehicleControls& controls, float dt) = 0;  // non-const
};

Mirrors path_tracking::IPathTrackingAlgorithm deliberately — the same pattern that lets 6 controllers plug in polymorphically now does the same for vehicle models. Deliberately minimal: earlier revisions also declared MaxStableDt(), DebugInfo(), and Name(), but none had any caller anywhere in the codebase, so all three were removed along with the now-dead DynamicBicycleModel class that also implemented them.

KinematicBicycleModel active — default

Rear-axle kinematics, no lateral tire slip. Equations byte-for-byte unchanged from before this work — it only gained IVehicleModel conformance (Step() lost const, gained override).

ComposedVehicleModel active

Composition root — 5 swappable subsystems (2× tire, suspension, drivetrain, aero, steering). Selected via ModelFidelity::DynamicLinearTire. Full detail below.

enum class ModelFidelity { Kinematic, DynamicLinearTire };

ComposedVehicleModel Deep Dive

→ See diagram page 3 — "ComposedVehicleModel — Composition and Step Flow"

The Five Subsystems

struct Subsystems {
    std::unique_ptr<ITireModel>       tire_front;
    std::unique_ptr<ITireModel>       tire_rear;
    std::unique_ptr<ISuspensionModel> suspension;
    std::unique_ptr<IDrivetrainModel> drivetrain;
    std::unique_ptr<IAeroModel>       aero;
    std::unique_ptr<ISteeringModel>   steering;
};

ITireModel LinearTireModel

Fy = clamp(coeff·Fz·α, ±μ·Fz)
coeff = TireParams::cornering_stiffness_coeff, μ = friction_coefficient.

ISuspensionModel RigidSuspensionModel

Fz_front = m·g·b/L − m·ax·h/L
Fz_rear = m·g·a/L + m·ax·h/L
h = VehicleData::cog_height (0 ⇒ static split only).

IDrivetrainModel DirectAccelDrivetrainModel

Fx = mass · u_a — bit-for-bit regression anchor vs. the pre-refactor behavior.

IAeroModel SimpleAeroModel

Fx = −mass · CA · vx·|vx| — bit-for-bit regression anchor vs. the pre-refactor behavior.

ISteeringModel Instantaneous / RateLimited

InstantaneousSteeringModel (default) or RateLimitedSteeringModel when steering.use_rate_limit — the latter finally activates max_steering_wheel_rate, parsed since day one but unused by any model until this work.

Step() Sequence

VehicleState ComposedVehicleModel::Step(state, controls, dt) {
    if (!actuator_seeded_) applied_steering_ = state.steering_angle;  // a rebuilt model keeps the wheel angle
    n = ceil(dt / 2 ms);                                              // explicit Euler is stiff at low speed
    for (i = 0; i < n; ++i) state = SubStep(state, controls, dt / n);
    return state;
}

VehicleState ComposedVehicleModel::SubStep(state, controls, h) {
    delta = UpdateSteering(controls.steering_angle, h);              // ISteeringModel — always first
    if (state.speed < kMinVx /* 0.5 m/s */)
        next = KinematicFallback(state, {delta, controls.acceleration}, h);
    else {
        loads = UpdateAxleLoads(last_ax_, state.speed);              // ISuspensionModel, uses PREVIOUS ax
        ComputeTireForces(delta, state, loads);                      // ITireModel × 2
        fx    = ComputeDrivetrainForce(...) + ComputeAeroForce(...); // IDrivetrainModel + IAeroModel
        next  = IntegrateDynamics(state, fx, delta, h);              // front force projected with delta;
    }                                                                // (x, y) = REAR AXLE: lateral vel. vy − b·r
    last_ax_ = (next.speed - state.speed) / h;
    next.steering_angle = delta;                                     // applied wheel angle, read by LQR/MPC/MPPI
    return next;
}

Every private helper is 2–20 lines, one level of abstraction — Step() itself is pure delegation. UpdateAxleLoads deliberately uses the previous step's longitudinal acceleration rather than solving an ax/Fz algebraic loop within one step — a one-step lag that also loosely approximates a real suspension's physical lag behind commanded acceleration.

Yaw inertia Iz_ = (data.yaw_inertia > 0) ? data.yaw_inertia : data.mass·a·b — computed once in the constructor. Both vehicle JSON files now set an explicit, literature-grounded yaw_inertia (see Data Model) rather than relying on the coarse two-point-mass fallback.

UI Integration & Live Tuning

→ See diagram page 5 — "UI Integration, Live Tuning and Tests"

A "Vehicle Model" picker lives on the simulation screen, not the main screen — deliberate: main-screen selections (vehicle/algorithm/map) are hard prerequisites that reset the whole scenario on change; model fidelity has a safe default and the actual use case is comparing fidelity mid-run, which requires not resetting.

selectedVehicleModelKind_, kAvailableVehicleModels = {"Kinematic", "Dynamic (Linear Tire)"}
modelDirty_  →  consumed lazily in TickSimulation(), exactly like paramsDirty_/RebuildAlgorithm()

RebuildVehicleModel():
    VehicleData vd = vehicle_loader_.GetVehicle();      // copy — never mutate canonical data
    if (tuneTire_.enabled)       { vd.tire.enabled = true; vd.tire.cornering_stiffness_coeff = ...; }
    if (tuneSuspension_.enabled) { vd.suspension.enabled = true; vd.cog_height = ...; }
    if (tuneSteering_.enabled)   { vd.steering.enabled = true; vd.steering.use_rate_limit = ...; ... }
    simModel_ = MakeVehicleModel(fidelity, vd);
    // simVehicleState_ deliberately left untouched — see below

Fidelity swap never resets simVehicleState_ — safe in both directions: Kinematic always writes lateral_speed=0 and a kinematic yaw_rate estimate every step, so handing those to a freshly-swapped dynamic model is the physically correct initial condition, not a hack. Going the other way, KinematicBicycleModel::Step never reads lateral_speed and only overwrites yaw_rate, so stale dynamic-model state is simply inert on the next step.

Bugs found & fixed during manual testing Panel collision: the new tuning panel's height budget was smaller than its actual content, visually overlapping the algorithm-tuning panel below it. Fixed by wrapping both panels' slider lists in their own bounded/scrollable ImGui::BeginChild regions.
Popup off-screen: the "Select Vehicle Model" popup opened anchored near its button (bottom-right of the panel), clipping off the window edge. Fixed by explicitly centering it via SetNextWindowPos(GetMainViewport()->GetCenter(), ...).

What's Not Implemented Yet

  • Level 3: quarter-car suspension (spring/damper states), torque-based drivetrain, per-corner (4-wheel) state, and the fixed-timestep-accumulator integration fix (explicit Euler becomes unconditionally unstable once a real suspension is added — not an issue yet since RigidSuspensionModel has no spring/damper states). No scaffolding for this exists in the codebase yet — it was removed as unused during a cleanup pass (see the note at the top of this document) and will be reintroduced when this work actually starts.
  • Level 4: no ABS/ESP overlay interface exists yet — none did before either implementation was needed, so none was added speculatively.
  • Nonlinear tire model: only LinearTireModel exists; ModelFidelity::DynamicPacejkaTire deliberately not added as an enum value yet.
  • tire.friction_coefficient is JSON-configurable but not exposed as a live UI slider.
